# Architecture PRD — Listing/Delisting Impact Analysis

Scope of this doc: app layout, functioning, and cosmetic/functional changes. For data/logic
rules (what a listing status means, how the knowledge base is built, dedup rules, etc.), see
[PRD_LOGIC.md](PRD_LOGIC.md).

**Convention:** every future cosmetic or functional change to the app gets a dated entry in
the Change Log at the bottom of this file, not just a code diff.

## Goal (as given 2026-09-21)
Build a new frontend, simple layout, for comparing sales across departments across stores,
with their previous listing histories tagged, using simplistic graphical notions.

## Current Architecture (Phase 2, v1)

- **Stack:** static HTML/CSS/vanilla JS in `app/` — no build step, no framework. Data is a
  pre-built static JSON file (`app/kb.json`) fetched client-side. Chosen because the dataset
  (~61k store×department combos × 42 months) fits comfortably in one static JSON blob — no
  backend/API needed for this phase.
- **Running it:** static files with `fetch()` calls need an HTTP server, not a double-clicked
  `file://` open (browsers block `fetch()` of local files under `file://`). Two ways to run it:
  1. **Auto-start at login (permanent, one-time setup)** — a Windows Scheduled Task,
     "Listing-Delisting App Server" (AtLogon trigger), runs `serve_silent.vbs` (a hidden-window
     VBScript launcher for `python -m http.server 8123` in `app/`) so `http://localhost:8123`
     is always reachable without manually starting anything. **Registering the task needs
     admin elevation that a normal Claude Code session doesn't have** (confirmed: a real
     Windows `Access is denied`, same reason `Buyer's Input Sheet`'s NSO Distributor Server
     task needed its own `REGISTER_..._AS_ADMIN.ps1`) — run `Register Server As Admin.ps1`
     once, as Administrator, to set it up. It also starts the server immediately as part of
     registering, and re-running it is safe/idempotent (`-Force` on the registration).
  2. **Manual, one session at a time** — double-click `Start App.bat` at the project root; it
     starts the same server in its own visible console window and opens the browser. Useful if
     you haven't run the admin registration yet, or want to see server logs. Leave that console
     window open while using the app; closing it (or Ctrl+C inside it) stops the server.
- **Layout:** single page —
  - Store selector + Department selector (searchable dropdowns, native `<datalist>`).
  - One heatmap grid: rows = stores (By Department tab) or departments (By Store tab),
    columns = months (Apr'23–Sep'26, whatever's in the listing KB). Each cell:
    - **background shade** = that store×dept×month's sales value (SL_V), blue intensity
      scaled relative to the max value in that row — this is the "compare sales" view.
    - **bottom border color** = listing status tag for that cell: green = Listed,
      red = Unlisted, gray = no listing record that month.
    - tooltip on hover shows store, department, month, listing status, and the sales figure.
- **Files:**
  - `app/index.html`, `app/app.js`, `app/style.css` — the frontend.
  - `app/kb.json` — listing history, generated by `scripts/build_knowledge_base.py`.
  - `app/sales.json` — sales by store/department/month, generated by `scripts/build_sales.py`.
  - `app/risk.json` — delisting-risk scores, generated by `scripts/build_risk_scores.py`.
  - None of the three JSONs are hand-edited; re-run the build scripts to refresh.

- **Drill-down:** clicking any row in either grid opens a modal with a single store×department
  trendline — native inline SVG line chart (no charting lib) of sales value across all months,
  with each point colored by that month's listing status (green/red/gray, same legend as the
  grid). Closes via the × button, clicking outside the card, or Escape.
- **Change Events tab:** a third tab listing every Y↔N listing transition in the dataset
  (store, department, change type, month, sales value before/after). Filters: store and
  department **multi-select dropdowns** (searchable checkbox panel, native platform widgets
  otherwise — no library), change type (All/Delisted/Relisted); sort: most recent or biggest
  sales impact (`|sales after − sales before|`). **Zero-impact events (₹0 both before and
  after the status flip) are hidden by default** — of 20,755 total events, 11,610 are zero-
  impact (a listing-flag change with no sales activity on either side, usually source-data
  noise rather than a real merchandising event) — a checkbox reveals them, and the count line
  always states how many are hidden so it's never a silent drop. Capped to the top 300 rows
  matching the current filters for render performance — narrowing filters reveals more.
  Clicking a row opens the same store×dept trendline drill-down as the grids.
- **Delisting Risk tab:** a fourth tab listing currently-Listed store×department combos whose
  recent in-season sales trend suggests delisting risk — score plus a **Low/Medium/High severity
  badge** (`.risk-badge`, traffic-light green/amber/red — tertiles of the flagged score
  distribution, see PRD_LOGIC.md), plain-English reason, prior in-season avg→recent avg sales,
  and how many in-season months back the score, ranked highest-risk first. Department names also
  carry the dynamic **In season/Off season badge** (see below), evaluated against that row's own
  `trend_through_month`. Data comes from `app/risk.json` (built by
  `scripts/build_risk_scores.py`); see PRD_LOGIC.md for the exact scoring rule and its
  limitations. Filters: search box (store/department substring), Season (All/In season/Off
  season), and severity select — all combine (AND); results capped to the top 300 matching rows
  for render performance, same pattern as Change Events. Clicking a row opens the same store×dept
  trendline drill-down as the other tabs/grids — no second chart was built.
- **Visual design system (cosmetic pass, no functional change):** adopted a Minimalism/Swiss-
  Style enterprise-dashboard direction from `ui-ux-pro-max`, via CSS custom properties in
  `:root` — `--color-primary` (#1e40af), `--color-secondary` (#3b82f6), `--color-accent`
  (#d97706), `--color-tertiary` (#7c3aed, added 2026-09-21 for the season-category badges below),
  `--color-quaternary` (#0891b2, added 2026-09-21, same reason), `--color-background` (#f8fafc),
  `--color-foreground` (#1e3a8a), `--color-card`/`--muted`/`--border`/`--destructive`.
  Listing-status colors (`--y`/`--n`/`--dot`) kept semantically separate from the palette
  tokens. Typography: Fira Sans
  (headings/labels) + Fira Code (every number — sales figures, risk %, chart axes; tabular
  monospace numbers are genuinely easier to compare down a column, not just decorative),
  loaded via Google Fonts `<link>`. Added: visible `:focus-visible` outlines on every
  interactive element (tabs, inputs, multiselects, table rows, modal close — previously
  keyboard nav had no visible focus state, an accessibility gap); a schematic Low→High
  gradient swatch next to the sales-shade legend (charting best practice: never leave a
  color-coded scale with no legend, even a relative one); 200ms hover/transition timing
  throughout. No HTML structure, data, or interaction logic changed.

- **Seasonality tab:** a fifth tab answering two calendar-month business questions for one
  picked department (searchable `<datalist>` input, same pattern as the other pickers) —
  *when are the natural listing/delisting windows?* and *if I bank on this department, when do
  I get the most growth?* Data comes from `app/seasonality.json` (built by
  `scripts/build_seasonality.py`); see PRD_LOGIC.md for the exact aggregation and its
  limitations. Layout: a bar chart (average sales by calendar month, Jan–Dec) reusing the same
  inline-SVG conventions as the trendline drill-down (same padding/axis/tooltip/color-token
  approach, just bars instead of a line+dots), then two ranked tables side by side — "Best
  growth periods" (up to 5 calendar months ranked by median month-over-month growth % arriving
  into them, each row showing which prior month it grew from and how many years back the figure
  — reworked 2026-09-21 to be month-keyed like the weak-periods table instead of a "Mon1→Mon2"
  pair, median instead of mean so one outlier year can't dominate, and declines are excluded
  rather than shown as "growth"; see PRD_LOGIC.md) and "Historically weak periods" (top 5 calendar months furthest below the
  department's own annual average, framed as delist/relist candidates). No drill-down (this
  view is already department-level across all stores, not a single store×dept combo) and no
  new chart library — same reuse discipline as the risk tab.

## Bug fixed this session
- **`hidden` attribute silently overridden by author CSS.** `#drill-modal { display: flex }`
  and `.controls { display: flex }` (on `#events-controls`, which has both classes) beat the
  browser's default `[hidden] { display: none }` rule via cascade source order — same-origin
  precedence, not specificity. Result: the drill-down modal has been rendering full-screen
  (empty) even while "closed" since it was added, and the events filter bar would have shown
  through on other tabs too. Fixed with one rule: `[hidden] { display: none !important; }`
  at the top of `style.css`. Caught only because this session screenshotted the actual closed
  state — checking `element.hidden` (the IDL property) doesn't catch this, since it just
  reflects the attribute, not what the CSS cascade does with it.
